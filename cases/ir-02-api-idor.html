API IDOR exposing customer data: proving who else used it

A researcher found that any logged-in user could read other customers' records through a commerce API. The fix shipped the same day. I led the investigation into whether anyone else had used it, with logs that didn't record what we needed by default.

Overview

A bug bounty researcher reported an insecure direct object reference (IDOR) in a commerce API. The endpoint checked that a login token was valid, but never checked that it belonged to the user being requested. With sequential user IDs, anyone with a free account could read any customer's contact details.

Engineering fixed it the same day. My job was the part that decides whether customers must be notified: did anyone other than the researcher read customer data, and over what period?

Why this matters

  • A bug bounty report with personal data is a privacy incident. The legal notification decision rests entirely on the IR analyst's log evidence.
  • The logs you need are often not the logs you have. Finding the right source and proving what a field means is half the work.
  • Attribution beats volume. The case closes only when every unexplained caller is explained.
  • Interview answer: "A researcher found a data exposure bug. How do you prove no one else exploited it?" This page is the answer.

Scenario

TriggerBug bounty report: authenticated IDOR on a commerce API
FlawToken validated, but token owner never compared to the requested user ID (broken object-level authorization)
Data at riskCustomer contact details: name, email, phone, postal address
GoalVerify the fix, find the real exposure window, attribute every cross-user read, and support the legal decision

Walkthrough

  1. Verify the fix independently

    With my own test account, I requested another user's record. It now returned 403. That check later doubled as a known event to validate the logs against.

  2. Find where the logs actually are

    The route turned out to be served by a different gateway than assumed, so the usual access logs had nothing. It also had no audit logging of the caller's identity. I worked with the gateway team to extract caller-level data from what that gateway did record.

  3. Prove what the log fields mean

    Before trusting the caller field, I matched it against my own fix-verification request. It showed up correctly as one failed cross-user request from my account, which confirmed the field identified individual accounts.

  4. Build a cross-user view per caller

    The key question per caller was how often they asked for a record that wasn't their own, and how often that succeeded.

    SELECT caller,
       COUNT(*)                                        AS requests,
       COUNT(DISTINCT target_id)                       AS targets,
       COUNTIF(target_id != caller_id)                 AS cross_user,
       COUNTIF(target_id != caller_id AND status=200)  AS cross_user_ok
FROM   gateway_requests
WHERE  route = '/users/{id}'
GROUP  BY caller
ORDER  BY cross_user_ok DESC

  5. Pin down the real exposure window

    Commit history showed the route had shipped without the check long before the report. But no frontend called it until a later product launch, and monthly request counts confirmed the route was essentially unused before then. The practical exposure window was much shorter than the code's age.

  6. Attribute every caller

    Each caller with cross-user reads was explained: the researcher's accounts, a backend service reading records by design, an internal verification account, and blocked attempts. One unknown account remained. I traced it to a tester reading its own sibling account from the same IP, so no customer data was involved.

  7. Use the baseline

    Normal traffic on the route was tiny, so enumeration stood out sharply. Only the researcher's account showed it.

  8. State the limits

    The report listed what the evidence could not show: log retention didn't cover the earliest period the route existed, the IP data was sampled, and related org-level routes were out of scope. Each limit came with the reasoning for why it didn't change the conclusion.

  9. Hand legal a clear answer

    Legal received a short summary of what happened, what the logs show, and what they can't show. Their no-notification decision was conditional on no non-researcher access, and the final attribution met that condition.

Outcome

  • Fix independently verified
  • Correct log source found and its fields validated against a known event
  • Real exposure window established from code history and request volume
  • Every cross-user read attributed; no customer data accessed by anyone other than the researcher
  • Legal confirmed no notification required
