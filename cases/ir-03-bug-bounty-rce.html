Bug bounty RCE: was it exploited before the report?

A researcher reported remote code execution on a public web app. AppSec confirmed the bug; my job was to prove whether anyone else had used it first.

Overview

A researcher reported remote code execution (RCE) on one of our public web apps through the bug bounty program. AppSec's job was to confirm the bug.

My job was the harder question: had anyone exploited it before the researcher told us? I turned the proof of concept into a fingerprint and searched our history for anyone else using it.

Why this matters

  • A fixed bug is not a closed incident. If the flaw existed for months, you have to show nobody else found it first.
  • The PoC is your best detection lead. It tells you exactly what malicious traffic looks like.
  • Researcher traffic must be separated from attacker traffic. Otherwise you either panic over the researcher or miss a real attacker.
  • Interview answer: "A bug bounty report says we have RCE. What does SecOps do?" This page is the answer.

Scenario

TriggerBug bounty report: RCE on a public web application
What we hadThe researcher's PoC request, test window and source IPs
Search windowFrom the release that introduced the flaw to the deployed fix
GoalProve whether anyone other than the researcher exploited it

Walkthrough

  1. Turn the PoC into a fingerprint

    I broke the PoC into the parts an attacker can't easily change: the endpoint, the HTTP method, the vulnerable parameter, and the payload pattern (command separators, encoded shell strings). That became the search signature.

  2. Fix the time window

    The window runs from when the flaw was introduced to when the fix shipped, not just the last few days. Log retention set the hard limit, and I recorded that limit as a caveat.

  3. Separate out the researcher

    I tagged every request from the researcher's reported IPs and test window. Anything matching the fingerprint from other sources became a lead.

  4. Search the edge logs

    I searched WAF and load balancer logs for the fingerprint across the whole window.

    path   = "/<vulnerable endpoint>"
method = "<METHOD>"
param contains any of  ;  |  $(  `  or base64-like strings
source_ip NOT IN (<researcher IPs>)

  5. Check the hosts for what RCE leaves behind

    Web logs only show attempts. To confirm execution, I checked the app hosts in EDR for the web process spawning shells or tools, unexpected outbound connections, and new files in web or temp directories.

    ParentProcess = <web server / app runtime>
ChildProcess IN (sh, bash, curl, wget, python, nc)

  6. Check the cloud side

    On the app's cloud identity, I looked for what an attacker does after RCE: metadata-service access, secret reads, and new keys.

  7. Report the verdict with its limits

    I wrote a short conclusion: what was searched, over what window, what was found, and what could not be checked.

Outcome

  • Exploit fingerprint built from the PoC and searched across the full vulnerable period
  • Researcher activity cleanly separated from all other traffic
  • No signs of post-exploitation on the hosts or in cloud audit logs
  • Fingerprint kept as a detection for future attempts
